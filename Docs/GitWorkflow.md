# Orris — Git Workflow

Status: repository convention
Version line: 0.1.0

## 1. Permanent and integration branches

| Branch | Role |
| --- | --- |
| main | Released, production-ready history. |
| develop/<version> | Integration branch for one explicitly approved version line. |

Current integration branch: develop/0.1.0.

## 2. Task branch naming

Every task branch uses a supplied task ID and specific short description:

~~~text
feature/ORR-xxx-short-description
fix/ORR-xxx-short-description
refactor/ORR-xxx-short-description
test/ORR-xxx-short-description
docs/ORR-xxx-short-description
chore/ORR-xxx-short-description
~~~

The task-ID prefix is ORR-. The numeric part and description are supplied by
task metadata; they are never generated by Codex.

hotfix/ is reserved for actual released production versions. Do not use vague
branches such as feature/new-ui, mail-work, test2, final, codex-changes, temp,
or fix-stuff.

Codex must never invent a task ID, branch name, release version, or version
bump. All four must come explicitly from task metadata.

Expected future task metadata:

~~~text
PROJECT
TASK
BRANCH
BASE
VERSION
~~~

## 4. Versioning

Orris uses Semantic Versioning. The current version line is 0.1.0. Versions
describe meaningful product/release state, not individual file changes.

- A version bump always requires explicit task authorization.
- Patch versions fix an established release baseline.
- A documentation change does not itself justify a version bump.
- This task leaves the version at 0.1.0.

## 5. Commits

Format:

~~~text
<type>: <specific change>
~~~

Allowed common types: docs, feat, fix, refactor, test, chore.

Examples:

~~~text
docs: establish Orris product baseline
feat: add multi-platform application bootstrap
fix: preserve inbox selection after refresh
refactor: isolate mailbox navigation state
test: cover unread inbox filtering
chore: configure project build settings
~~~

Do not use update, changes, fix, stuff, working, final, or codex changes as a
commit message.

## 6. Branch preflight and delivery safety

Before editing:

1. Run git rev-parse --show-toplevel, git branch --show-current, git status
   --short, and git log -1 --oneline.
2. Verify the exact Git root, requested base branch, expected task branch
   absence/presence, and intended working-tree scope.
3. Stop on unrelated modifications. Do not stash, reset, restore, clean, or
   overwrite them.
4. Create the supplied task branch before changing the base branch.

Before committing:

1. Review git status --short, git diff for intended files, git diff --stat,
   changed-file list, and warnings relevant to the task.
2. Run the smallest applicable build/test checks and verify runtime behavior
   when the task changes runtime behavior.
3. Documentation-only tasks may explicitly mark build/runtime checks not
   applicable.
4. Stage only task files; never use git add ..

Do not push, merge, tag, rewrite history, or amend unrelated history unless
the task explicitly authorizes that action.

## 7. Repository Hygiene

Generated and user-specific files must not enter commits. The repository-local
`.gitignore` defines Orris's known generated-file and user-local ignore policy;
global Git ignore or configuration is not a substitute for repository policy.
Inspect unexpected untracked files found during preflight before any deletion
or cleanup. Codex must never automatically delete an unexpected user file just
because it is untracked.

Shared Xcode project configuration, `xcshareddata`, and shared schemes remain
version-controlled. `Package.resolved` remains version-controlled for the
Orris application when Swift Package dependencies are introduced.
